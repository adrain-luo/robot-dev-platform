# 阶段 2a：运控核心独立成进程

> 2026-11-26。计划和负责人的决定（D1–D8）见工作区的 `阶段2计划.md`。**还没上过机器人**；默认仍是 `--motion-core inprocess`（现状）。

## 1. 是什么

| 进程 | 启动 | 写执行器 |
| --- | --- | --- |
| 运控核心 | `python -m g1_motion_core.service ...` | 唯一：直写后端时写 `rt/lowcmd`（G1D）/ `rt/arm_sdk`（G1）；守护层后端时是守护层唯一的客户端 |
| 网页 | `python serve.py --motion-core ipc ...` | 手臂不写（不建指令出口、不听指令话题）；立柱、底盘、吸盘在 2a 里仍由网页发 |

两者在同一台机器上，经 Unix 套接字通信（`/run/g1-motion/core.sock`，急停单独走 `estop.sock`），格式见 `src/g1_contracts/wire.py`。

**崩溃后果**

| 哪个进程崩溃 | `inprocess`（现状） | `ipc`，直写后端 | `ipc`，守护层后端 |
| --- | --- | --- | --- |
| 网页 | 网页就是写入者：停发，**掉臂** | 核心照常发帧；网页的租约撤销，网页手动走着的手停在指令角，拖拽中的手全刚度锁住 | 同左 |
| 运控核心 | — | 核心就是写入者：停发，**掉臂** | 守护层原地保持 |

**负责人定的数值（2026-11-26，D5）**：客户端每 50 ms 发一次心跳；核心 250 ms 收不到某个连接的任何消息，就撤销它的租约、停住它手动动着的手；连接断开立即撤销。改这两个数要先问负责人（`tests/test_contracts_wire.py` 会提醒）。

**和计划的出入**：计划里写"核心按 50 Hz 推送状态"。实现改成页面和任务按需取状态（一次请求一次应答），因为任务在 `move_to` 之后马上读 `status()` 要看到刚下的目标；推送的缓存可能是旧的，会让"等到位"误判已经到了。核心只主动推送租约撤销（`lease_event`）。

## 2. 离线跑（这台机器、mock）

```bash
export G1_MOTION_DIR=/tmp/g1-motion
python -m g1_motion_core.service --backend mock --instance /path/to/instance &
python serve.py --backend mock --motion-core ipc --instance /path/to/instance
```

两个进程必须用同一个实例（`--instance`）：负载补偿、TCP、碰撞检查用的数据都在实例里。mock 不给 `--instance` 时各自建临时实例，数据对不上。

mock 下两个进程各有一个仿真机器人，只有核心那个在动；网页显示的实测角来自核心。网页的 `/api/mock/foreign`（模拟别的写入者）在 ipc 时只影响网页自己的仿真，核心看不到。

测试：`python -m pytest tests/test_motion_core_server.py tests/test_motion_client.py tests/test_web_ipc.py tests/test_contracts_wire.py`。

## 3. 操作卡 A：Box 上第一次跑（直写后端，G1D）

> **由负责人执行。** 前提：**手臂有机械支撑**，有人守着断电；Box 上没有别的程序写 `rt/lowcmd`（refactor 节点不在跑，`fatigue.service` 已停）。
> 运控核心退出时会像现在的网页退出一样释放手臂：直写后端下就是停发，手臂会掉。所以停核心之前手臂要有支撑。

1. 停掉现在跑的 `serve.py`（它是写入者；手臂要有支撑）。
2. 起核心（前台，方便看日志）：
   ```bash
   export G1_MOTION_DIR=/tmp/g1-motion   # 默认 /run/g1-motion 要 root 建；2d 的 systemd 单元会建它
   python -m g1_motion_core.service --allow-real-motion --instance <实例名>
   ```
   看到 `listening on /tmp/g1-motion/core.sock` 和 `max_speed=0.2`。
3. 另开终端（同样 `export G1_MOTION_DIR=/tmp/g1-motion`）起网页：`python serve.py --allow-real-motion --motion-core ipc --instance <实例名>`，打开页面。
4. 页面：接管 → 走一个小目标 → 急停 → 复位急停。核心日志里应有 `E-STOP from web:...`。
5. **杀网页**（手臂接管、正在走一个小目标时）：`kill -9 <serve.py 的 pid>`。
   - 期望：手臂停在半路、不掉、不抖；核心日志 `disconnected: web:...` 和 `held right`。
   - 重新起网页，页面应显示"已接管"（核心一直接管着）。
6. 收尾：页面「释放」（手臂有支撑），再 Ctrl-C 停核心。
7. 发回：核心日志、页面截图、第 5 步手臂的表现。

回滚：停掉两个进程，照旧 `python serve.py --allow-real-motion`（不加 `--motion-core`）。

## 4. 操作卡 B：守护层后端（等守护层过了上机清单）

同操作卡 A，核心加 `--backend guardian`。另外看：

- 页面急停后守护层也锁存（`python -m g1_guardian.client --host 192.168.123.164 status` 里 `state` 是 `estop`）；复位要两步：「复位急停」解除核心，「接管」时确认复位守护层。
- **杀核心**（`kill -9`）：守护层原地保持，手臂不掉；守护层日志 `latched:link_lost`。这一步只在守护层后端下做。
- 守护层锁存时会写黑匣子。在这台开发机上，同进程测试里锁存前后的帧间隔偶尔到 40–50 ms（虚拟机调度抖动加写黑匣子的线程抢 GIL）。本体上请看守护层状态里的 `loop.max_ms`，急停前后各记一次。
