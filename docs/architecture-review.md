# G1/G1D 平台架构评审：视觉与运控边界、进程与交付

Nov 23, 2026 · @Adrain

## 结论摘要

真正的问题不是“视觉和运控要不要拆”，而是每台机器上的运动发令者不唯一。视觉早就是独立进程（本体主机上的 18081 服务），而 rt/lowcmd 的写入方至少有四套实现。

推荐的目标形态：

- **一台机器一套运控核心**：分两层（第十三节）。本体侧执行守护层是唯一的 DDS 写入者，负责限位限速、看门狗和断联保持；Box 侧运控核心负责租约仲裁、碰撞闸门、重力与负载前馈。手臂、腰、底盘、立柱、末端 IO 都只经它下发。
- **其余按故障域合成三个进程**：任务进程、感知进程、运维网关。不做微服务。
- **代码按包模块化**：多仓库 + 发布清单，接口包统一版本，依赖方向由 CI 和运行环境强制。
- **视觉闭环用“带有效期的流式目标”**：视觉按自己的节奏改目标，核心按 100–200 Hz 插值；目标过期就减速保持，任务进程崩溃就撤租约保持。
- **交付单位是“发布清单”**：一组带版本和哈希的运行包、模型包、机型包。标定数据留在机器上，不进任何包。研发、正式、售后、标定四个版本共用同一份运控核心构建。

第一件该做的事不是重构，而是让急停和断联都变成“保持”而不是“停发”。按已确认的断流行为，refactor 现在按急停会让手臂掉落（第十三节）。

## 一、提问方式本身隐含的假设

这个问题把“代码怎么切”当成了核心，但代码里的证据指向的是发令权、停止协议和主机拓扑。下表逐条列出隐含前提。

| 隐含前提 | 实际情况 | 照这个前提做会怎样 |
| --- | --- | --- |
| 代码包 = 进程 = 服务 = 运行包 = 交付包 | 这是五个独立决定。动作库可以是独立发布包，却跑在任务进程里；运控核心是独立进程，却和任务共用同一个接口包。 | “多一个包”会被做成“多一个服务”，部署面和故障面成倍增加。 |
| 视觉与运控是“拆”或“不拆”二选一 | 代码依赖上必须解耦；时间、坐标系、标定版本上必须紧耦合。要拆的是“谁能发令”，不是“谁和谁说话”。 | 会漏掉时间戳和状态历史这些真正决定闭环精度的东西。 |
| 视觉频繁调用运控会有性能问题 | 本机 IPC 往返通常在亚毫秒级；一次视觉请求包含拍照、推理、PnP，慢两个数量级以上。现在真正的开销是每次调用都新建一次 SSH 连接（`hal/ssh_utils.py`），而且就在写 lowcmd 的同一进程里。 | 为省 IPC 把视觉塞进控制进程，正好把最重、最不稳定的负载放到了控制循环旁边。 |
| 动作越多，服务越多 | 增长的是动作条目，不是进程。动作应当是“数据 + 少量技能代码”，跑在同一个任务进程里。 | 停止、仲裁、版本兼容都变成 N 方协调问题。 |
| 架构问题主要是代码整洁问题 | 拆分的首要理由是安全和故障域。现在急停是协作式的软件暂停，任务线程不配合就慢（见第三节）。 | 得到漂亮但不安全的结构。 |
| 当前目录结构就是未来产品边界 | 平台的目录“和网页左右两侧的分区对应”（README），`App` 由十个 mixin 拼成。这是研发调试形态。 | 把 UI 的偶然结构固化成产品接口。 |
| “视觉模块”是一个模块 | YOLO\_YAN\_COORDINATION 里还有底盘位姿微调（18084）、本体动作（body\_control）、浏览器遥控（18086）、BLE 遥控（root 运行）、吸盘代理（18080）。其中四个会让机器人动。 | 把它当“视觉”拆出去，等于把一批发令者也放到了运控之外。 |
| 只有进程边界，没有主机边界 | 实际是 Box 跨网络给本体发 lowcmd；诊断记录了两端持续上涨的 UDP 接收缓冲错误；EARLY\_PLAN 时间修复要求两台主机上三个组件同时更新。 | 主机边界带来时钟、网络、部署原子性问题，比进程边界更难，必须先定。 |
| 不带源码 = 保护好了 | Python 字节码可被还原，混淆只能提高门槛。更紧迫的是不带源码时售后还能诊断。 | 先混淆、后做符号和日志，现场问题将无法复现。 |
| 这是一个系统 | 三个仓库各自发展。平台最新提交是“Import latest robot platform state from robot host”，真相源在机器人上；AnyGrasp 支撑服务“不在任何 git 仓库里”（`待办.md`）。 | 没有唯一真相源，就谈不上版本回滚。 |

## 二、重新定义的问题

假设上表的前提全错，问题应当这样问：

> 在 Box 与本体两台主机、三个仓库并存的现状下，如何让每台 G1/G1D 上每类执行器只有一个发令者；让视觉、动作库、工作流、标定和网页都只能通过一个带租约、限幅、时间戳和安全状态的接口请求运动；并让这套软件以不含源码、可离线安装、可一键回滚的清单交付，同时保证研发凭符号、日志和黑匣子能复现现场问题？

它拆成五个子问题，顺序即优先级：

1. **发令权**：哪个进程、在哪台主机上，是手臂、腰、底盘、立柱、末端 IO 的唯一写入方？
2. **安全责任**：保护性停止、急停、断流各自由哪一层实现，哪一层是最后一道防线？
3. **协作契约**：视觉与运控之间传什么、带什么时间和坐标系、过期了怎么办？
4. **扩展方式**：新动作怎样只加数据和技能，而碰不到发令层？
5. **交付单元**：什么东西一起发布、一起回滚，什么数据属于机器而不属于版本？

“视觉和运控要不要拆”是第 1、第 3 个子问题的一个结果，不是出发点。

## 三、现状诊断：真实的耦合点

运控逻辑本身容易抽出，平台的 `ArmLoop` 已经基本是运控核心的形状。难的是发令权收口、停止协议和任务对 `App` 的依赖。

证据来自附件 `vision_arm_control_refactor`（下称 refactor）、`robot-dev-platform`（下称平台）和 `YOLO_YAN_COORDINATION`（下称视觉仓库）。

| # | 耦合点 | 证据 | 后果 | 拆解难度 |
| --- | --- | --- | --- | --- |
| 1 | 运控实现不唯一 | refactor `hal/arm_driver.py`（200 Hz）；平台 `control/arm_loop.py`（100 Hz）；refactor `scripts/` 下两个本体侧执行服务（lowcmd、arm\_sdk）；部署文档里的 coupled-IK 服务；诊断还发现 `fatigue.service` 带 250 Hz lowcmd 发布者 | G1D 的 lowcmd 没有权重混合，两个写者直接打架（平台 `cmd_monitor.py` 注释） | 中：要收敛成一套 |
| 2 | refactor 没有单一写线程 | 每段轨迹、每次 hold 在调用线程里各跑一个循环；`stop_persistent_hold` 等 1 s 超时就丢下旧线程；无写锁（`diagnostics/README.md` 已确认该机制） | 交接时可能两个循环同时写 | 低：换成单线程模型 |
| 3 | 急停是协作式的 | refactor：E\_STOP 与任务走同一个 String 话题，先等任务线程停（上限 10 s）再暂停；`pause_control` 不发新帧只停发，并异步释放吸盘。平台：`routes._hold` 要逐个调用各任务的 stop，任务仍持有占用权，在 `estop_hold` 之后再下一步目标，循环照收 | 急停时间取决于任务代码配不配合；“暂停”的实际效果取决于固件对断流的处理 | 中：核心加锁存与租约撤销 |
| 4 | 控制循环与重负载同进程 | refactor 每次读视觉、查吸盘、调底盘、调立柱都新建一次 paramiko 连接；平台把网页、cv2、IK、碰撞放在一起，已经被迫把多初值 IK、碰撞、雷达挪进子进程（“不占主进程 GIL，控制循环不卡”） | GIL、加密和 CPU 抖动直接进入控制周期 | 低：搬出核心即可 |
| 5 | 没有状态新鲜度门控 | 两套都只在启动时等首帧 lowstate；平台 `snapshot()` 只查是否为空，`age_s()` 只用于网页显示 | lowstate 中断时循环照常用旧值发令 | 低 |
| 6 | 任务通过 App 拿一切 | `BoardTouch(self)`、`PayloadAPI(self)`、`DetectLocalize(self)`；任务读写 `app.loop`、`app.kin`、`app._work_pose_motion`；refactor 的 `ArmTaskNode` 同时持有手臂、视觉、吸盘、底盘、立柱、规划、执行和 ROS | 任何任务都能碰到任何东西；每加一个动作就要改急停路由 | 高：最重的耦合 |
| 7 | 依赖方向反了 | `perception/detect_localize.py` 从 `tasks/board_touch.py` 导入私有函数 `_fit_plane`、`_sample_point` | 感知依赖任务，无法单独发布 | 低 |
| 8 | 接口无类型、无版本 | `/arm_control/task_command` 上同时出现 `std_msgs/String` 和 `g1d_arm_msgs/ArmTaskCommand`，日志反复报反序列化错误；EARLY\_PLAN 修复要三端同时部署 | 升级只能整体同时换，无法单独回滚 | 中 |
| 9 | 底盘与立柱多发令者 | 本体侧 body\_control、pose\_adjust、remote\_control、BLE 遥控都通过子进程调 SDK 程序；平台有 `chassis_control`、`lift_control`；refactor 经 SSH 调立柱和位姿微调 | 手臂伸出时谁能动底盘，没有统一联锁 | 中 |
| 10 | 配置、数据、凭据混在源码里 | 同一组 Kp 在三处各写一份（目前一致，`README_zh.md` 里的值已过期）；`instances/*/calib` 进 git；模型 `.pt` 放在视觉仓库（整库 332 MB）；SSH 密码认证加 `AutoAddPolicy`；平台网页默认绑 0.0.0.0 且无鉴权 | 交付时无法只换代码或只换数据 | 中 |

诊断包本身就是为间歇性 lowcmd 控制中断而建的，操作卡里的事件标记叫 `arm_drop_observed`。上表第 1、2、4、5 条都是它的候选原因，这说明架构问题已经在现场表现为安全问题。

可以直接继承的好底子：

- 平台的边界规则（只有 `hw/` 发 DDS），`ArmLoop` 的单写线程、限速、占用者和统一碰撞闸门入口，`CmdMonitor` 用 CRC 识别第三方发令。
- refactor 的 `hal / planning / execution / node` 分层和依赖规则；诊断包有哈希校验恢复、操作卡和单变量对比，质量很高。
- 18081 已上报模型 SHA256 与来源，会拒绝过期帧；EARLY\_PLAN 修复还做了跨主机时钟映射，联合 IK 一侧不确定度超过 20 ms 就拒绝。
- 平台的 `instances/` 是“机器数据”边界的雏形；`mock` 后端可用于离线测试。
- refactor 的 stage-B 执行服务验证的正是“发令循环靠近 DDS、上层只发轨迹”这个方向。

## 四、十个问题：总工与研发负责人的视角

总工关心“出事时谁兜底”，研发负责人关心“团队怎么天天干活不破坏它”。两者结论一致时不重复。

### 1. 视觉与运控在哪里解耦、在哪里协作

- **总工**：必须解耦的是发令权和故障域。视觉永远不直接写执行器，视觉崩溃不能让手臂失控。必须紧密协作的是时间（同一时钟或已知映射）、坐标系（同一 URDF 与标定版本）和状态（视觉结果要配上拍照那一刻的关节角）。
- **研发负责人**：解耦落在包依赖上：感知包不导入任何运控包，运控包不导入感知包。协作落在接口包的几个类型上：带时间戳的观测、坐标系 ID、标定版本引用。

### 2. 各层负责什么

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| 低层运控（核心） | 唯一发令；插值与限速；限位；碰撞闸门（检查）；重力与负载前馈；状态新鲜度与看门狗；急停锁存；租约仲裁；状态历史与黑匣子 | 视觉、任务语义、IK 搜索、绕行规划这类长计算 |
| 视觉闭环（一类技能） | 观测到目标的换算（用拍照时刻的关节角）、IK、收敛判据、超时与放弃 | 直接写关节、自己做限速 |
| 动作库 | 用参数化技能组合出可命名、可校验、可版本化的动作 | DDS、增益、话题名、电机号 |
| 工作流 | 动作顺序、分支、重试、人工确认、业务状态 | 运动细节 |
| 标定工具 | 采集、求解、质量评估，写入带来源的新标定版本 | 在线改正在生效的标定 |

- **总工**：碰撞“检查”在核心里，是闸门；碰撞“绕行规划”在技能侧，算完交给核心复查。现在 `set_target(detour=True)` 把两者放在了同一个调用里。
- **研发负责人**：核心 v1 只收关节空间目标，IK 全在技能侧。核心越小，安全评审越快。

### 3. 视觉闭环如何频繁调用运控

- **总工**：频率分三层：核心 100–200 Hz、视觉 1–30 Hz、任务按事件。视觉每次只“改目标”，不“开新运动”。目标带有效期，过期即减速保持；任务心跳丢失即撤租约保持。限速限位在核心里，与目标来自谁无关。
- **研发负责人**：用流式目标接口，不要每次走“规划 + 确认”的到位接口。核心保留约 2 s 状态历史，供技能按拍照时刻取关节角。18081 拒绝过期帧的规则保留。测试用 mock 核心注入延迟和丢帧。接口见第七节。

### 4. 代码包、进程、发布包怎么切

- **总工**：进程按故障域切，只切粗；运控核心单独成进程，是为了让安全逻辑可以单独评审和冻结。
- **研发负责人**：代码包按依赖规则切，可以切细；发布包按发布节奏和评审级别切。三者不要求一一对应。表见第六节。

### 5. 模块化单体、控制核心 + 视觉进程，还是微服务

- **总工**：选 B 的收敛版。微服务会把安全逻辑分散到多个服务，责任边界变模糊。
- **研发负责人**：代码按 A 组织，进程按 B 切。视觉仓库在本体上定义了 8 个服务、6 个 HTTP 端口，已经是无协调的 C，要收不要放。对比见第五节。

### 6. 当前是否容易拆解，最重的耦合在哪

- **总工**：最危险的是第三节第 1、3 条：多发令者和协作式急停。这两条不先解决，拆什么都不安全。
- **研发负责人**：最费工的是第 6 条：任务对 `App` 的依赖。核心本身容易抽，任务要一个个改成只拿接口。

### 7. 如何逐步迁移

- **总工**：每一步都要能单独上线、单独回滚；任何一步都不能让机器人在过渡期里有两个发令者。
- **研发负责人**：顺序是先收发令权、再在进程内定接口、再搬进程、再做动作库、最后做发布工程。新接口外包旧实现，逐个替换调用方。阶段见第十节。

### 8. 研发版、正式运行版、现场售后版、标定版

- **总工**：四个版本的运控核心必须是同一份构建。售后和标定如果换了核心，现场复现的就不是客户那份代码。
- **研发负责人**：差异只在附加包和授权；版本不是四条分支。详见第九节。

### 9. 源码、标定、日志、符号、模型、运行包、历史版本放哪

- **总工**：标定属于机器，代码属于版本。标定要绑定机器序列号、机型包版本和相机序列号，不符就拒绝加载。
- **研发负责人**：源码和符号只在公司；运行包和模型在制品库，现场保留当前版和上一版。表见第九节。

### 10. 动作增长不重新耦合到 DDS

- **总工**：停止靠核心撤销租约，不靠动作自觉。这样动作再多，急停路径也不变。
- **研发负责人**：物理隔离：任务进程的运行环境里不安装 `unitree_sdk2py`，CI 检查导入规则，动作尽量是数据。详见第八节。

## 五、三种方案对比

推荐 B 的收敛版：代码按 A 组织，进程按 B 切，只有当某部分有独立的硬件归属（如 GPU 感知）或故障域时才多一个进程。C 的代价在当前团队规模下不划算。

| 维度 | A 模块化单体 | B 运控核心独立 + 视觉与动作层独立 | C 多服务 / 微服务 |
| --- | --- | --- | --- |
| 实时性 | 控制循环与网页、cv2、IK 抢 GIL；平台已被迫把计算外移到子进程 | 核心进程独占 CPU 核、用实时调度，抖动可测可控 | 与 B 相同，但链路更长，跨服务调用叠加延迟 |
| 安全性 | 任一模块异常可拖垮发令线程；急停依赖各模块配合 | 限幅、锁存、租约集中在一个小进程，可单独评审和冻结 | 安全逻辑容易被分散，谁对停止负责说不清 |
| 故障隔离 | 一个进程一个故障域 | 视觉、任务、网页崩溃都只导致“保持” | 隔离最细，但级联超时和半可用状态最多 |
| 视觉闭环适配 | 调用最便宜，但视觉负载就在控制循环旁 | 流式目标 + 有效期，IPC 开销可忽略 | 每次修正跨多跳，时间戳和时钟对齐最难 |
| 动作库扩展 | 容易，但也最容易直接碰到 loop 和 DDS | 动作跑在任务进程，只能经客户端发令 | 动作被做成服务后，停止与仲裁变成分布式问题 |
| 部署复杂度 | 最低，一个服务 | 4 个服务，可控 | 高；视觉仓库的 8 个服务已呈现这种形态 |
| 升级与回滚 | 只能整体换 | 核心慢节奏、应用快节奏，按清单整体回滚 | 版本矩阵膨胀，需要服务级兼容管理 |
| 现场调试 | 一个进程好查，但故障无法定位到模块 | 每进程独立日志 + 核心黑匣子，边界清楚 | 要分布式追踪才看得清一次动作 |
| 研发成本 | 现在最低，以后最高 | 一次性投入接口和进程化 | 最高，团队规模不支撑 |
| 适合阶段 | 单台研发样机 | 小批量交付到量产早期 | 多机型、多团队、有云端编排的后期 |

注意 A 的“调用最便宜”是假优势：视觉闭环的瓶颈在视觉延迟和时间对齐，不在调用开销。

## 六、推荐的目标架构与五种边界

一台机器一套运控（本体守护层 + Box 运控核心），另有任务、感知、运维三个进程；代码按包组织，多仓库加发布清单（第十三节）。五种边界各自独立，下面分开列。

&#91;embedded content: 目标架构 · 5 个进程，1 个写入者\]

所有写执行器的箭头都从运控核心出发。任务、感知、网页任何一个崩溃，结果都只是“保持”；只有本体守护层失效会掉臂，而手臂没有硬件急停可以兜底。

### 逻辑模块边界

1. **设备适配**：Unitree DDS、AGV 与立柱、吸盘等末端 IO。
2. **运动权威**：仲裁、限幅、闸门、前馈、看门狗、急停锁存、黑匣子。
3. **机器人模型与运动学**：URDF、FK/IK、碰撞模型、绕行规划（纯计算，核心与技能共用）。
4. **感知**：相机、识别、双目、点云、雷达，输出带时间戳的观测。
5. **技能与动作库**：参数化的运动能力和由它们组成的动作。
6. **工作流**：任务状态机。
7. **标定**：采集、求解、质量评估。
8. **运维**：网页、诊断、日志导出、升级。
9. **机器数据**：标定、工作姿态、空间点、自定义动作。

## 七、视觉与运控之间的接口示例

视觉不直接调运控：视觉产生带时间戳的观测，技能把观测换算成关节目标，再用租约发给核心。下面是接口包里的核心类型（示例，字段名可调）。

```python
# g1_contracts/motion.py —— 技能与运控核心之间的唯一接口
from dataclasses import dataclass
from enum import Enum
from typing import Optional, Sequence

CONTRACT_VERSION = "1.0"

class Resource(str, Enum):
    RIGHT_ARM = "right_arm"; LEFT_ARM = "left_arm"; WAIST = "waist"
    CHASSIS = "chassis"; LIFT = "lift"; RIGHT_TOOL = "right_tool"

@dataclass(frozen=True)
class Stamp:
    t_ns: int                # 产生该时间的主机单调时钟
    host: str                # "body" / "box"
    uncertainty_ns: int = 0  # 映射到核心时钟的不确定度

@dataclass(frozen=True)
class LeaseRequest:
    resources: Sequence[Resource]
    owner: str               # "skill:visual_align/task-0412"
    heartbeat_ms: int = 300  # 超过这个时间没有心跳就撤销

@dataclass(frozen=True)
class Lease:
    lease_id: str
    epoch: int               # 急停或撤销后递增；旧 epoch 的指令一律拒绝

@dataclass(frozen=True)
class StreamSetpoint:        # 视觉闭环用：只改目标，不开新运动
    lease_id: str
    epoch: int
    seq: int
    resource: Resource
    q: Sequence[float]       # v1 只收关节角，IK 在技能侧
    derived_from: Stamp      # 生成该目标的观测拍照时刻
    valid_for_ms: int = 200  # 核心收到后计时；过期未刷新就减速保持
    speed_scale: float = 1.0 # 只能在核心限值之内再降

@dataclass(frozen=True)
class GoalRequest:           # 到位类：可带绕行路径，核心会复查
    lease_id: str
    epoch: int
    resource: Resource
    path: Sequence[Sequence[float]]
    timeout_ms: int

class Verdict(str, Enum):
    ACCEPTED = "accepted"; CLAMPED = "clamped"; REJECTED = "rejected"

@dataclass(frozen=True)
class Ack:
    seq: int
    verdict: Verdict
    reason: str = ""         # stale_epoch / collision / limit / estop_latched / stale_observation

@dataclass(frozen=True)
class MotionState:           # 核心按控制频率发布，并保留约 2 s 历史
    stamp: Stamp
    q_meas: Sequence[float]
    q_cmd: Sequence[float]
    lease_owner: Optional[str]
    safety: str              # normal / hold / estop_latched / stale_lowstate
```

视觉闭环技能的用法：

```python
with motion.lease([Resource.RIGHT_ARM], owner=f"skill:visual_align/{task_id}") as L:
    while not converged(err):
        obs = perception.latest(label, max_age_ms=150)      # 带拍照时刻
        q_then = motion.state_at(obs.stamp).q_meas           # 拍照那一刻的关节角
        p_torso = to_torso(obs, q_then, calib=active_handeye)  # 用当时的关节角换算
        q_goal, err = ik.solve(p_torso, seed=L.last_q)
        ack = L.stream(Resource.RIGHT_ARM, q_goal,
                       derived_from=obs.stamp, valid_for_ms=200)
        if ack.verdict is Verdict.REJECTED:
            raise SkillAborted(ack.reason)                   # 带上拒绝原因
```

核心一侧的规则：

- **每个周期**：查 lowstate 年龄 → 取当前有效目标 → 限位与碰撞检查 → 限速插值 → 叠前馈 → 写帧 → 记黑匣子。
- **目标过期**：减速到零并保持，状态报 `hold`，不算错误；新的有效目标到来自动继续。
- **观测太旧**：`derived_from` 距现在超过阈值（含不确定度）就拒绝，原因 `stale_observation`。
- **心跳超时或急停**：epoch 加一、撤销租约、保持；旧 epoch 的指令全部拒绝。这就堵住了平台现在“`estop_hold` 后任务还能再下一步”的窗口。
- **急停锁存**：只有核心本地确认后才解除，任务和网页都不能解除。
- **每个资源只有一个写者**：网页手动点动也先拿租约；平台现有的 owner 机制就是这个的雏形。

传输可以是 ROS2 自定义消息，也可以是 Unix socket 加 msgpack。不论选哪种，类型定义、接口版本、序号、时间戳缺一不可；现在的 String JSON 不满足。跨主机时，有效期用“核心收到后计时”，避免依赖两台主机的时钟一致；观测时间继续用 18081 已有的时钟映射。

## 八、动作库的分层

动作库分五层，越往下越少、越稳、评审越严；动作数量的增长只发生在第 3、4 层。

| 层 | 是什么 | 例子 | 谁能改 | 变更成本 |
| --- | --- | --- | --- | --- |
| 0 设备适配 | DDS 与设备协议 | lowcmd 帧、AGV 升降、吸盘命令 | 运控小组 | 安全评审 + 实机回归 |
| 1 核心动词 | 核心对外的固定小集合 | hold、goal、stream、tool\_io、set\_payload、teach | 运控小组 | 安全评审 |
| 2 技能 | 经客户端调用核心动词的 Python 代码，参数有 schema | move\_to\_named\_pose、approach\_along\_axis、cartesian\_line、visual\_align、suction\_on\_verify、lift | 应用研发 | mock 核心测试 + 评审 |
| 3 动作定义 | 引用技能与命名姿态的数据文件 | pick\_box\_right、board\_touch\_9x6 | 应用工程师，客户在限定范围内 | schema 校验 + 仿真 |
| 4 工作流 | 动作的顺序、分支、重试、确认 | 取货 → 放货 → 复位 | 应用工程师 | 仿真 + 现场试运行 |

动作定义示例（下降高度、抬升高度、吸附超时取自 refactor 当前默认值，其余为示意）：

```yaml
action: pick_box_right
version: 3
requires: [right_arm, right_tool]
params:
  target_label: {type: str, from: perception.labels}
  lift_m: {type: float, min: 0.02, max: 0.12, default: 0.08}
steps:
  - skill: move_to_named_pose
    pose: work_pose/右手取货        # 从机器实例存储取，不写死关节角
  - skill: visual_align
    target: ${target_label}
    tolerance_mm: 5
    timeout_s: 8
  - skill: approach_along_axis
    axis: down             # 从目标上方沿直线下降
    distance_m: 0.17
  - skill: suction_on_verify
    timeout_s: 3
  - skill: lift
    distance_m: ${lift_m}
on_abort: hold_then_report
```

防止动作库重新耦合到 DDS 和控制代码的规则：

- 动作定义里不允许出现话题名、增益、电机号、原始 DDS 字段；schema 校验直接拒绝。
- 任务进程的运行环境里不安装 `unitree_sdk2py`，想导入也导入不了；CI 再加一道导入检查。
- 新增动作 = 新增数据 + 仿真校验；新增技能 = 代码 + mock 核心测试 + 评审；新增核心动词 = 安全评审。
- 停止靠租约撤销。急停路由不再需要列举每个任务的 stop，平台 `routes._hold` 里的 stoppers 列表可以删掉。
- 每个技能声明占用的资源和中止行为，工作流据此判断能否并行（左右手各跑一个动作）。
- 现有的工作姿态、空间点、单姿态、姿态集已经是实例里的数据文件，直接作为动作定义引用的“命名姿态”。

## 九、交付：四种版本与资产存放

四种版本不是四条代码分支，而是同一份发布清单加不同的附加包和授权；运控核心在四个版本里是同一个哈希。

### 四种版本

| 版本 | 给谁 | 包含 | 不含 | 启用方式 |
| --- | --- | --- | --- | --- |
| 研发版 | 研发、公司样机 | 全部源码与 Git、mock 后端、直连 DDS 工具、诊断补丁、全部调试页 | — | 只装在公司资产机器上 |
| 正式运行版 | 客户现场操作员 | 清单锁定的运行包、模型包、机型包、动作库；操作员网页；黑匣子；诊断包导出 | 源码、Git、测试、直连 DDS 工具、参数编辑 | 默认安装 |
| 现场售后版 | 售后工程师 | 正式版 + 售后附加包：只读 DDS 探针、lowcmd 诊断、回放、参数查看与受控修改、全量日志导出 | 源码；不替换核心 | 限时授权文件，操作留审计 |

refactor 的诊断包（`diagnostics/lowcmd_diag.sh`）已经是售后附加包的样子：只读、有哈希校验、可恢复、有操作卡。差别是它现在靠改源码文件生效，以后要改成核心自带的可开关采集。

### 资产放在哪

| 资产 | 真相源 | 现场有什么 | 版本方式 |
| --- | --- | --- | --- |
| 源码与 Git 历史 | 公司代码仓库（不是机器人主机） | 无 | Git 标签对应构建号 |
| 运行包（wheel 等构建产物） | 公司制品库 | 当前版 + 上一版 | 构建号 + 哈希 |
| 符号与调试信息（源码快照、依赖锁、行号映射） | 制品库，按构建号永久保存 | 无 | 与构建号一一对应 |
| 发布清单 | 制品库 | 每个已装版本一份 | 清单版本号 |
| 模型（`.pt`、TensorRT 引擎） | 模型库，不放 Git | 当前版 + 上一版 | SHA256（18081 已上报）；引擎按设备型号分别构建 |

| 动作库内容 | 制品库；客户自定义部分在实例存储 | 随清单 + 本机自定义 | 动作版本号 |

| 历史版本 | 制品库全量 | 只留两份 | 回滚 = 切回上一份清单 |

### 现场安装布局与升级

```text
/opt/g1/releases/2026.12.0/   # 一份清单一个目录，只读
    venv/  packages/  manifest.json
/opt/g1/current -> releases/2026.12.0
/var/lib/g1/instance/          # 标定、工作姿态、空间点、自定义动作（升级不碰）
/var/lib/g1/blackbox/  /var/log/g1/
```

升级代理的流程：校验离线包签名与接口兼容 → 解到新目录 → 停服务 → 切链接 → 自检（核心只读自检、不接管）→ 失败就自动切回。当前“`git pull` + 重启”和“手工备份、替换、重启三个服务”的方式，都由这一步取代。

关于源码保护：已确认不是重点，不做混淆或编译。运行包的作用是可复现、可回滚；符号与源码快照仍按构建号留在公司，便于对照现场的异常堆栈。

现场问题复现的路径：诊断包带回清单版本、实例数据快照和黑匣子 → 研发从制品库拉同一份清单与符号 → 在 mock 后端或公司样机上回放。

## 十、从当前代码开始的迁移阶段

五个阶段按顺序做，每个阶段都能单独上线、单独回滚；阶段 2 之前不新拆任何进程。

1. **阶段 0：收口发令权（不重构）**
   - 每台机器同一时刻只允许一个发令进程：systemd 互斥，启动前用 `CmdMonitor` 检查话题占用；把 `CmdMonitor` 移植到 refactor。

   - 每次新建 SSH 连接改为长连接，或改为局域网 HTTP 加鉴权。
   - 网页加鉴权，默认只绑内网口。
   - **退出门槛**：运行期间没有第三方发令告警；下一次掉臂能在诊断数据里定位到原因类别。
2. **阶段 1：定接口，先在进程内走通**
   - 新建 `g1_contracts`；在 `ArmLoop` 外包一层 MotionCore 接口：租约、epoch、stream、goal、`state_at`、急停锁存。
   - 所有任务改拿 MotionClient（先用进程内实现）；`App` 不再把自己传给任务，改为注入客户端、只读运动学和实例存储。
   - 把 `_fit_plane`、`_sample_point` 搬到公共几何模块，修掉感知对任务的反向依赖。
   - 急停改为撤销租约；删掉 `routes._hold` 里逐个调用 stop 的列表。

   - MotionClient 换成 IPC 实现；核心单独成 systemd 服务（实时调度、绑核、watchdog）。
   - refactor 的 PICK/PLACE 时序改写成技能，调用同一个核心；停用 refactor 自己的 lowcmd 写入。stage-B 执行服务演化成本体守护层（第十三节修订一）。

   - **退出门槛**：故障注入全部通过——杀任务进程手臂保持；停视觉后目标过期、减速保持；杀网页不影响急停；控制周期抖动达到总工定的指标。
4. **阶段 3：动作库与工作流**
   - 棋盘触摸、空间点、工作姿态、吸盘取放改写成技能 + 动作定义。
   - 视觉闭环技能用流式目标 + 有效期；底盘的三段式位姿微调也改成同一种技能。
   - **退出门槛**：新增一个动作不改核心和 hal 代码；动作定义的 schema 校验进 CI。
5. **阶段 4：发布工程与四种版本**
   - 仓库与包拆分完成；CI 产出带签名的运行包、清单、符号包；模型进模型库；实例数据迁出 Git。

   - **退出门槛**：在一台干净机器上离线装出正式版，升级和回滚演练通过；售后用一份诊断包在公司复现一次现场问题。

## 十一、当前最不应该做的三件事

1. **在唯一发令权建立之前拆进程或做微服务。** 把任务、标定、感知、网页各拆成服务，只会把现在的“多写者 + 协作式急停”变成跨进程、跨主机的版本。先做阶段 0 和阶段 1。
2. **大爆炸式重写，或一次性合并三个仓库再上机。** refactor 的取放时序、吸盘校验、失败自动复位是实机验证过的，平台的碰撞模型和标定工具也是。用新接口包住旧实现，逐个替换调用方。
3. **先做源码混淆和加密打包。** 在可复现构建、符号、黑匣子和发布清单之前做混淆，售后会失明，现场问题无法复现，而换来的保护并不可靠。

顺带一条：在这些问题解决之前，不要再给同一台机器新增任何会写执行器的程序。

## 十三、按确认结果修订

第十二节的回答改变了两个判断：急停和断联都必须变成“保持”而不是“停发”；运控核心要拆成本体和 Box 两层。其余回答大多是收窄范围。

### 改变判断的事实

- lowcmd 断流时手臂失能掉落；手臂没有硬件急停，软件急停是最后一道防线。
- 运控核心在 Box，经网络给本体发 lowcmd。网线、交换机、Box 上的进程，任何一处中断都等于断流。
- 由此推出两个现有问题（按你们的实测行为推断，未上机验证）：
  - refactor 的 E\_STOP 调用 `pause_control`，它停止发帧；同时异步释放吸盘。**按急停会让手臂和物体一起掉落。**
  - 平台的 `estop_hold` 继续发帧并锁在当前角度，方向是对的。但 G1D 的“释放”在 lowcmd 后端没有过渡，循环停发后手臂同样掉落。
- 运控核心目前一个人开发：核心必须尽量小，每一步迁移都要一个人做得完。
- 碰撞检测不稳定、对外关闭，所以它目前不是安全功能；安全功能是位置、速度、加速度限制。

### 修订一：运控核心拆成本体与 Box 两层

你提的“hal 单独部署本体”方向对，但放到本体的不应只是 hal，而是任何一处失效就会掉臂的全部逻辑。划分规则：**失效会导致掉臂的放本体，计算重或常改的放 Box。**

| 层 | 主机 | 职责 | 上游失联时 |
| --- | --- | --- | --- |
| 执行守护层 | 本体，独占 CPU 核、实时优先级 | 唯一 DDS 写入（lowcmd 或 arm\_sdk，含 arm\_sdk 权重渐变）；固定 200 Hz 发帧；位置、速度、加速度限制；增益上限；lowstate 新鲜度；目标看门狗；急停锁存；黑匣子环形缓存 | 减速到零、保持当前角度、持续发帧；锁存“上游失联”，本地复位后才继续 |
| 运控核心 | Box | 租约仲裁与联锁、碰撞闸门（启用时）、重力与负载前馈计算、把目标插值成 50–100 Hz 设定流、状态历史、对任务的接口 | 由守护层兜底 |
| 任务、感知、运维 | Box；感知在本体 GPU | 不变 | 由运控核心处理（见第七节） |

- 守护层从 refactor 的 stage-B 执行服务演化而来，不是新写。它应当足够小、很少改动，一个人也维护得了。
- 重力前馈在 Box 算，随设定一起下发。守护层保持时沿用最后一帧前馈，姿态不变时它仍然有效。
- Box 到本体的设定流带序号和有效期；守护层自己插值到 200 Hz，网络抖动就不会直接变成关节抖动。
- Box 上的开发和调试方式基本不变，符合“测试便于迁移”的要求。
- 本体上占满一个核的可视化服务要绑到其他核，或改为按需启动。

### 修订二：急停与吸盘的建议

建议把“停”分成四级。每级的手臂和吸盘行为都写死在守护层或运控核心里，不由各个任务自己处理。

| 级别 | 触发 | 手臂 | 吸盘 | 怎么恢复 |
| --- | --- | --- | --- | --- |
| 暂停 | 操作员暂停、视觉目标过期 | 减速保持 | 保持 | 自动或操作员继续 |
| 保护停止 | 超限、lowstate 过期、租约超时、上游失联 | 减速保持，任务中止 | 保持 | 操作员复位 |
| 急停 | 网页急停；底盘硬件急停（如能读到） | 立即锁在当前角度，持续发帧 | 保持 | 本地确认后复位 |
| 安全放下 | 操作员在保持状态下单独发起 | 慢速移到放置高度或休息姿态 | 到位后释放 | — |

吸盘的建议：**急停时保持吸附，不释放。** 急停时手臂停在半空，释放就是让物体从这个高度掉下去，可能砸到人脚或货物。急停的原则是“停止运动，不改变其他状态”。需要释放时，走单独的“安全放下”，由操作员确认周围安全后发起。如果某个场景里被吸住的物体本身就是危险源，就给它单独一个释放按钮，不要做成急停的副作用。

另外两条直接相关：

- 底盘硬件急停的状态如果能从 SDK 读到，守护层应订阅它：按下时手臂也进入急停保持。这样一个按钮停全身。是否能读到，需要确认。
- G1D 的“释放”改成两段：先移到休息姿态（或提示有人扶住），再确认释放；或者在几秒内逐步降低 Kp，而不是直接停发。

### 修订三：“控制周期抖动”指什么、怎么验收

指的是**发帧时间的抖动**，不是 PID 引起的机械振动或不收敛。200 Hz 下两帧之间应间隔 5 ms；GIL、垃圾回收、SSH、网络都可能让个别间隔变长，长到一定程度就是断流。机械振动是增益问题，发帧抖动是调度和网络问题，两者要分开测。

发帧抖动的验收建议：

1. 先实测“断流多久手臂失能”，记为 T\_drop。这是固件特性，G1D 的 lowcmd 和 G1 的 arm\_sdk 要分别测。
2. 在本体侧统计发帧间隔的 p50、p99、最大值，以及超过阈值的次数。refactor 的 `diagnostics/lowcmd_runtime` 已经能统计间隔，可以直接复用。
3. 验收条件：满负载（视觉、网页、任务同时运行）连续运行若干小时，最大间隔远小于 T\_drop（例如不超过一半），且超过两个周期的间隔次数有上限。具体数值由你们定。

机械振动那一侧，把你们的经验写进机型包：G1D 手臂 Kp 超过 250 出现明显高频振动，150–180 无明显抖动，演示用 210。机型包给默认值和上限，现场微调写入实例存储并留记录，守护层按上限钳位。这一侧按你说的，用人的感知、视觉和实机测试来衡量。

### 修订四：传输与时钟

传输继续用 ROS2 自定义消息。核心只有一个人维护，不应再引入第二套中间件。要改的是用法：

- 一个话题只有一种类型，消息包带版本号；修掉 `/arm_control/task_command` 上 String 与 ArmTaskCommand 混用的问题。
- 急停单独一个话题或服务，不和任务指令共用。
- 设定流用 best-effort + keep\_last(1)；租约、到位、急停用 service 或 action。
- 确认 ROS2 与 Unitree DDS 是否在同一个 DDS domain。如果是，ROS2 的发现和话题流量会和 lowcmd、lowstate 共用网卡与接收缓冲；诊断记录的 UDP 接收缓冲错误，值得往这个方向查一次。

时钟用 chrony。客户内网没有外网，就让 Box 做本地时间源（`local stratum`），本体同步到 Box。局域网内一般能到亚毫秒级，对 1–30 Hz 的视觉足够。现有的请求应答时钟映射保留为运行时自检：两者偏差超过阈值时，把观测标为不可信。只有需要更高精度、且网卡支持硬件时间戳时才用 PTP。

### 修订五：多仓库 + 发布清单

接受多仓库，第六节里“一个仓库”的建议作废。要让多仓库也能一起回滚，需要三样东西：

- 接口包（ROS2 消息 + Python 类型）单独版本化，各仓库在依赖里锁定版本；接口一变，版本号必须跟着变。
- 一个很小的清单仓库，只记录一组联调过的组合：各仓库标签、构建哈希、模型哈希、机型包版本。交付和回滚都按清单走。
- 清单仓库的 CI 用 mock 后端跑一遍跨仓库的接口测试。

Python 环境按仓库各自打包（例如 conda-pack 或 venv），不强制统一；统一的只有接口包。

### 修订后的前三步

1. **refactor 的 E\_STOP 改成保持**：急停时继续发帧、锁在当前角度，不再走停发的 `pause_control`；吸盘默认保持。改动小、风险最大，最先做。平台 G1D 的“释放”同时加过渡。
2. **把 stage-B 执行服务做成本体守护层**：固定频率发帧、限位限速、目标看门狗、上游失联保持，并成为本机唯一写入者。
3. **再做第十节的阶段 1**：接口包与租约，用 ROS2 消息实现。

这三步做完，“按急停掉臂”和“Box 或网络一断就掉臂”都会消失；之后的阶段顺序不变。
